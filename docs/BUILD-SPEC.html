The two-sided bench

Vendors run agents over their bench. Clients run agents over their requirements. Hand this page to a Base44 engineer and they can build it.

0

Can you build this in Base44?

Yes

For the first version, Base44 is a good fit. It has the database, login, file storage, scheduled jobs and — importantly — Workflows, which runs multi-step automation triggered by a data change. That is exactly what a loop needs.

What you need and Base44 has: entities with relations, role-based login, file upload for resumes and documents, LLM calls, email, scheduled tasks, webhooks, and Workflows for the loops.

The one thing that matters: you cannot get your backend out.

Base44 exports your frontend code to GitHub. The backend and database stay on their infrastructure. If you leave, you rebuild the back half.

So do two things from week one. Keep the data model plain and portable. And write a weekly job that dumps every entity to your own S3 bucket as JSON. Your match history and outcome data is the only asset that compounds — never let it live in one place you don't control.

Two smaller cautions.

The database is MongoDB-style, not relational. Fine for this. It gets awkward later when you do financial reconciliation, so keep money records simple and flat.

Don't write long-running agent processes. Model every loop as a status field on a record, where each agent call moves it one step. That's how Base44 Workflows wants to work, and it's better engineering anyway — every step is restartable and every step is logged.

1

Why this is better than what I proposed

Earlier I warned you off building a marketplace. That warning does not apply here, and I want to be clear about why.

I was talking about a market for AI agents, where there are no buyers and no sellers yet. Building that is suicide.

IT staffing is the opposite. Vendors have benches today. Clients have requirements today. Billions change hands every year. Nothing needs to be created — the matching and the paperwork are just slow and painful.

You're not starting a market. You're speeding up one that already runs.

And there's a second reason this is stronger: the vendor side is useful on its own. A staffing firm gets value on day one from triage and faster submissions, even if no client ever joins. That solves the cold start completely.

AgentRun is not logging. It is the product.

It records what each agent tried, whether it passed, and what it cost. Without it you cannot tell whether the thing works, what a submission costs you, or which agent to fix.

Every founder skips this table and regrets it in month four. Build it in week one.

What to hand the engineer

This page, plus the brief below. It's written to be pasted into Base44 as the opening instruction.

Build a multi-tenant app for IT staffing agencies.

TENANCY
Every record carries org_id. Users see only their own org's records,
except Submissions, which the receiving client org can also read.
Roles: vendor_admin, recruiter, client_admin, hiring_manager.

ENTITIES
Organization, User, Consultant, Document, Requirement, Distribution,
Submission, AgentRun, Check, Outcome, VendorScore, RateBenchmark.
(Fields as listed in the data model table.)

THE CORE PATTERN — read this twice
Do not write long-running agent processes. Each agent is ONE short
LLM call that reads a record, writes a result, and moves the record's
status one step forward. Loops are Workflows triggered by a status
change. Every single call writes one AgentRun row with verdict,
cost and duration — no exceptions, including failures.

SUBMISSION STATUS MACHINE
draft -> checking -> needs_fix -> checking -> ready -> submitted
      -> screening -> shortlisted | rejected -> outcome_recorded
"needs_fix" loops back to "checking" a maximum of 3 times, then it
raises a task for a human. Never loop without a cap.

FIRST BUILD — vendor side only
Screens: Bench board, Requirement inbox, Submission builder,
Agent activity log.
Agents: bench profile builder, requirement triage, submission checker.
Requirements are pasted in by hand for now. No client side yet.

NON-NEGOTIABLE
1. AgentRun is written on every call, pass or fail.
2. A weekly scheduled job exports every entity as JSON to external
   storage.
3. The submission checker must use rules where a rule will do —
   rate ranges, document presence, date validity. Only use the LLM
   for judging whether a skill claim is actually evidenced in the CV.

That last point matters more than it looks. Half the checks are arithmetic and date comparison. Use code for those. They're free, instant and always right. Save the model for the one judgement it's actually needed for.

Start with one vendor and their bench. Everything else follows from that working.
